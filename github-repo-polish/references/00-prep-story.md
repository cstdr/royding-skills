# 阶段 0: 准备 —— 采集你的故事

> **这一步不是技术活,是聊天。** 全部素材必须由你本人提供,AI 不能编。
> 大约 10-15 分钟,但决定了阶段 4 / 6 / 7 的"活人感"质量。

## 为什么必须先做这一步

绝大多数 AI 生成的 README 看起来假,是因为里面**没有"我"**。全是"modern / blazing-fast / type-safe"这种通用话术,放哪个项目都能用。

让一个仓库看起来"维护用心"的核心是:**作者愿意在 README / Issue / 注释里讲自己的判断、踩坑、犹豫**。这种内容 AI 没法编,因为它不知道:

- 你为什么做这个项目(不是市场分析,是个人痛点)
- 你选了什么技术栈,放弃过什么(以及为什么)
- 哪个功能你其实还不满意,但先发了
- 哪个 bug 你追了三天才找到

这些只能你讲。下面 8 个问题,建议在脑子里过一遍,或者用任意记事本写下要点再告诉我。

## 必答 8 问

### Q1: 这个仓库解决你**自己的**什么痛点?

不要写"解决行业 X 问题",要写"**我自己**每天手动 Y 操作,烦了"。

✅ 好例子:
> "我每天早上要把 5 个 git 仓库的分支切到 main 拉新代码,攒了一周忘了就冲突,所以写了个 alias 跑一遍。"

❌ AI 腔:
> "提供现代化的多仓库协作管理方案,提升团队效率。"

### Q2: 你是怎么开始做的?第一版是什么样的?

讲"丑陋的第一版"是活人感利器。多数大牛的 README 都有这种"v0.1 就 200 行硬编码"的诚实。

✅ 例子:
> "第一版是 Bash 脚本,300 行,if-else 嵌套到我自己都看不懂。后来重构成 Go,加单元测试,才敢开源。"

### Q3: 哪些技术栈是**主动选择**的?哪些是**被动妥协**?

大牛的特征是:能讲清楚"为什么是 X 不是 Y"。即使选错了,也讲清楚当时的 reasoning。

✅ 例子:
> "本来想用 Rust,但团队没人熟,部署也麻烦,选了 Go。性能上 Rust 会快 3 倍,但这个项目 IO 是瓶颈,选 Go 更划算。"

### Q4: 你**砍掉**了哪些功能?为什么?

讲"做减法"比讲"加了什么"更显成熟。

✅ 例子:
> "本来想做 GUI,但用 CLI + shell alias 的人更多,GUI 维护成本高、bug 多,先不做。如果有人 issue 提需求再考虑。"

### Q5: 哪个部分你**还不满意**?

承认不足 = 活人感。AI 写的 README 全是优点,真人写的会有"这块写得不好,见笑了"。

✅ 例子:
> "测试覆盖率只有 40%,核心 CLI 跑过,边角的配置文件解析没测。如果你要在生产用,自己再补一下。"

### Q6: 你希望什么样的人来用 / 提 issue / 提 PR?

不要写"欢迎所有人"。要具体。

✅ 例子:
> "如果你也用 tmux + vim,大概率会喜欢这个工具。如果你不用 vim,可能用不顺手,提 issue 我会考虑加配置。"

### Q7: 你的下一步打算?(roadmap)

Roadmap 不要写 5 年大计。写近 1-2 个月想做的,而且标注"还在犹豫要不要做"。

✅ 例子:
> "短期:
> - [ ] 加 `--dry-run` 选项
> - [ ] 修复 macOS 上偶尔段错误的问题(reproduce 不出来,有点难)
> - [ ] 也许加 fish 支持?看需求。"

### Q8: 你的联系方式 / 主页?喜欢哪种风格?

- Twitter / X handle
- 个人网站(强烈推荐,即使是一页)
- 邮箱(注意:GitHub Issue 暴露邮箱会被爬,可以放 mastodon / bluesky)
- 你写代码以外的事(独立游戏 / 写作 / 画画),这一栏很多人会加

## 怎么把这些素材喂给 skill

**方式 A(推荐):** 在阶段 4 / 6 / 7 时,AI 问"为什么做这个",你直接粘上面某题的答案。

**方式 B:** 把答案写在一个 `STORY.md`(不进 git),AI 按需读取。这样多个阶段能复用。

**方式 C:** 不写文档,直接口述。最自然但要 AI 边问边记。
